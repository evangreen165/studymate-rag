# 2 ПРЕДВАРИТЕЛЬНАЯ ОБРАБОТКА И АНАЛИЗ ДАННЫХ

## 2.1 Сбор и подготовка данных

Источником данных является локальная база учебных материалов, собранная для курса. Она содержит {{DOCS}} PDF-файлов по семи темам. Файлы не публикуются в открытом репозитории, поскольку являются авторскими учебными пособиями; в репозитории хранятся манифест с хешами, паспорт корпуса и скрипты сборки. Для демонстрации в репозиторий включён небольшой синтетический корпус из семи конспектов (CC BY 4.0), чтобы система запускалась без полного набора книг.

Паспорт датасета содержит следующие сведения: источник, состав, язык, формат, объём, число страниц, распределение по темам, ограничения и способ предобработки. Сводные показатели приведены в таблице 2.1.

**Предобработка.** Для извлечения текста используется PyMuPDF. Для каждой страницы сохраняется номер, что позволяет в дальнейшем ссылаться на конкретное место документа. Выполняются следующие шаги:

1. Проверка PDF на шифрование и попытка открытия с пустым паролем.
2. Извлечение текста постранично.
3. Удаление повторяющихся колонтитулов: строк, которые встречаются в начале или конце более 25 % страниц документа.
4. Удаление строк, состоящих только из номера страницы.
5. Нормализация пробелов и пустых строк.
6. Расчёт статистики: число символов, доля кириллицы, число страниц с малым объёмом текста.
7. Дедупликация: точные дубликаты определяются по SHA256 файла, близкие повторы — по хешу нормализованного текста чанка.

Результат сохраняется в кэш `data/cache/extracted/` в формате JSON: для каждого документа хранятся страницы с текстом. Это ускоряет повторную индексацию и позволяет строить EDA без повторного обращения к PDF.

## 2.2 Разведочный анализ данных

EDA выполнен по манифесту и извлечённому тексту. На рисунке 2.1 показано распределение документов и страниц по темам. Видно, что корпус сильно несбалансирован: алгоритмы и сети дают более половины всех страниц, а Git — менее 0,1 %. Это влияет на retrieval: вопросы по Git требуют точного поиска по небольшим шпаргалкам, а вопросы по алгоритмам — смыслового поиска по большим учебникам.

![Распределение документов и страниц с текстом по темам](docs/images/eda-topics.png)

На рисунке 2.2 приведены 15 крупнейших документов. Три документа («Linux API. Исчерпывающее руководство», «Компьютерные сети» Таненбаума и «Компьютерные сети» Олифера) дают около 4 700 страниц с текстом. При этом в корпусе есть две версии учебника Олифера, что создаёт риск дублирования фрагментов при поиске.

![Топ-15 документов по числу страниц с текстом](docs/images/eda-documents.png)

**Пропуски и сканы.** Пять документов не имеют пригодного текстового слоя: «SQL за 10 минут» (335 страниц), «Основы технологий баз данных» (304 страницы), «Алгоритмические трюки» (509 страниц), «Вычислительная математика для IT» (128 страниц) и ещё один документ с частичным текстом. Они исключены из индекса, но остаются в паспорте корпуса. На рисунке 2.3 показаны документы с наибольшим числом страниц, содержащих менее 200 символов; это титульные листы, разделители, страницы с рисунками и сканы.

![Документы с наибольшим числом страниц без текста](docs/images/eda-lowtext.png)

**Дубликаты.** Точных дубликатов по SHA256 не обнаружено, однако есть содержательные повторы: две версии учебника Олифера, а также архив `git.zip`, содержащий копии всех PDF. Архив исключён из обработки, а текстовые хеши чанков позволяют не индексировать одинаковые фрагменты дважды. Дублирование страниц — одна из причин, по которой число страниц в паспорте ({{PAGES}}) больше числа страниц с текстом ({{TEXT_PAGES}}).

**Язык.** Доля кириллицы в большинстве документов составляет 0,80–0,98. Четыре шпаргалки по Git полностью англоязычные (доля кириллицы 0,00), что учитывается при выборе эмбеддингов: модель должна поддерживать русский и английский языки.

**Чанкинг.** Текст разбивается на чанки с помощью `SentenceSplitter` из LlamaIndex. Размер чанка — 800 токенов токенизатора USER2, перекрытие — 100 токенов. Использование токенизатора модели эмбеддингов важно: стандартный tiktoken для кириллицы даёт примерно в два раза больше токенов, из-за чего чанки получаются слишком короткими. После перехода на токенизатор USER2 средняя длина чанка составила около 1 570 символов, а общее число чанков — {{BM25_CHUNKS}}. Распределение длин и сравнение размеров индексов показаны на рисунке 2.4.

![Распределение длины чанков и размеры индексов](docs/images/eda-chunks.png)

**Выявленные ограничения данных:**

- часть PDF — сканы без текстового слоя;
- формулы и таблицы при извлечении теряют структуру;
- в корпусе есть английские шпаргалки и русские учебники с английскими терминами;
- тематическая несбалансированность: Git и ООП представлены слабо;
- две версии одного учебника создают риск дублирования;
- метаданные PDF не всегда содержат корректное название, поэтому название очищается и при необходимости берётся из имени файла.

## 2.3 Углублённый анализ качества входных данных

Дополнительно проведён анализ по подгруппам. Для каждого документа рассчитаны: число страниц, доля страниц с текстом, средняя длина страницы, доля кириллицы и число страниц с низким объёмом текста. Результаты показывают, что качество корпуса неоднородно:

- **Linux.** Книга «Linux API. Исчерпывающее руководство» содержит 1 238 страниц с текстом и даёт наибольший вклад в плотный индекс; «Расширения ядра Linux» — 680 страниц. Обе книги технически сложные, с большим количеством кода и системных вызовов.
- **SQL.** Восемь документов имеют текстовый слой, один — скан. Книги различаются по уровню: от «SQL за 10 минут» (скан) до «Проектирование и реализация СУБД» (466 страниц). Это создаёт разброс сложности вопросов.
- **Алгоритмы.** 17 документов, из них несколько сканов. Корпус включает учебники по алгоритмам, регулярным выражениям, математическому программированию и тестированию; часть материалов выходит за рамки базового курса.
- **Сети.** Четыре крупных учебника и две книги по веб-хакингу и сокетам. Вопросы по сетям требуют различения уровней OSI, протоколов и конкретных реализаций.
- **Git.** Только шпаргалки, поэтому ассистент может отвечать на вопросы о командах, но не на глубокие вопросы о модели ветвления: в корпусе нет учебника Pro Git.
- **Computer Science и ООП.** По одному учебнику; покрытие хорошее для базовых понятий, но ограничено.

Для оценки устойчивости к «зашумлённым» входам проверялись страницы с формулами, таблицами и листингами кода. Установлено, что формулы могут превращаться в последовательность символов, а таблицы — в набор строк без связей. Это снижает качество поиска по формулам и коду; частично проблема решается тем, что ответ формируется по нескольким фрагментам, а не по одному.

Интерпретация решений модели на уровне входных данных включает анализ того, какие страницы попадают в контекст. Для этого в интерфейсе показываются документ, страница и оценка релевантности, а в результатах оценки сохраняются источники для каждого вопроса. Это позволяет отличить ошибку поиска (нужная страница не найдена) от ошибки генерации (страница найдена, но модель добавила лишнее).

## 2.4 Разбиение данных

В RAG нет параметрического обучения, поэтому «обучающая», «валидационная» и «тестовая» выборки имеют другую природу, чем в классическом ML:

- **обучающая выборка** — корпус документов, который индексируется и доступен для поиска; метки классов отсутствуют;
- **валидационная выборка** — 10 вопросов с эталонными ответами, используется для выбора top-k, размера чанка и версии промпта;
- **тестовая выборка** — 30 вопросов (по 4–5 на тему), не используется при подборе параметров; на ней рассчитываются итоговые метрики.

Вопросы составлены по страницам корпуса с помощью LLM и затем проверены вручную: вопрос должен быть понятен без чтения фрагмента, а эталонный ответ — полностью содержаться в материале. Для каждого вопроса сохранены тема, документ, страница и эталонный ответ. Тестовая выборка не пересекается с валидационной. Такое разбиение соответствует методическим рекомендациям с поправкой на генеративную природу задачи: тестовая выборка отделена от настройки, а корпус выполняет роль источника знаний.
