# 3 АРХИТЕКТУРНОЕ РЕШЕНИЕ

## 3.1 Описание и схема компонентов системы

StudyMate построен как набор слабо связанных компонентов (рисунок 3.1). Пользователь работает с веб-интерфейсом Streamlit, который обращается к REST API FastAPI. API вызывает RAG-ядро: оно выполняет поиск по двум индексам, формирует промпт и обращается к LLM. Плотный индекс хранится в ChromaDB, разреженный — в BM25-корпусе. Ответ возвращается в API вместе с источниками и метриками, а UI отображает его в чате.

![Архитектура интеллектуальной системы](docs/images/architecture.png)

Компоненты системы:

- **Streamlit UI** — чат, история, управление корпусом, метрики. Не содержит бизнес-логики поиска, общается с API по HTTP.
- **FastAPI** — валидация запросов, маршрутизация, коды ошибок, OpenAPI, CORS, JSON-логи, Prometheus-метрики.
- **RAG-ядро** — маршрутизация по теме, гибридный поиск, MMR, взвешенное объединение, фильтрация оглавлений, построение контекста, промпт, разбор цитат, отказ при отсутствии контекста.
- **ChromaDB** — персистентное хранилище плотных векторов с метаданными (документ, тема, страница).
- **BM25-корпус** — разреженный индекс по всем чанкам, не требует эмбеддингов и покрывает весь текст.
- **USER2-base** — модель эмбеддингов (768 измерений), русскоязычная, на базе ModernBERT.
- **LLM** — Llama-3.1-70B через OpenRouter; резерв — локальная Qwen2.5-7B в формате GGUF.
- **PDF-корпус и ingestion** — PyMuPDF, очистка, чанкинг, кэш извлечённого текста.

На рисунке 3.2 показан пайплайн обработки: офлайн-подготовка индекса и онлайн-обработка запроса. На рисунке 3.3 — диаграмма вариантов использования: студент задаёт вопросы, смотрит источники, фильтрует по теме, работает с историей; администратор загружает материалы, запускает индексацию, удаляет документы и смотрит метрики.

## 3.2 Обоснование выбора моделей

**Модель эмбеддингов.** Выбрана `deepvk/USER2-base` — русскоязычная модель на базе ModernBERT, обученная на парах запрос-документ и данных Russian NLP. Она имеет 768 измерений, распространяется по лицензии Apache-2.0 и поддерживается `sentence-transformers`. Модель хорошо подходит для корпуса, где 80–98 % текста — русский, но встречаются английские команды и термины.

Сравнение кандидатов приведено в таблице 3.1. `intfloat/multilingual-e5-base` — универсальная многоязычная модель, но на русских учебных текстах уступает специализированной USER2. `BAAI/bge-m3` показывает высокое качество, однако требует больше памяти и времени на CPU. `USER2-small` быстрее, но даёт меньшую точность на длинных технических фрагментах. Выбор USER2-base — компромисс между качеством, лицензией и возможностью работать на CPU.

**Генеративная модель.** Основная модель — `meta-llama/llama-3.1-70b-instruct` через OpenRouter. Она поддерживает русский язык, имеет контекст 131 072 токена, доступна по цене около $0,72 за миллион токенов и хорошо следует инструкции «отвечай только по контексту». Резервная модель — `meta-llama/llama-3.3-70b-instruct`; при недоступности OpenRouter можно использовать локальную `Qwen2.5-7B-Instruct-Q4_K_M` (4,68 ГБ), которая работает на CPU, но медленнее и менее точна.

## 3.3 Обоснование выбора архитектурного подхода

Сравним четыре подхода (таблица 3.3): классический ML (TF-IDF + логистическая регрессия), дообучение encoder-модели, zero/few-shot LLM без поиска и RAG.

| Таблица: Сравнение архитектурных подходов
| Критерий | Classical ML | Fine-tuning encoder | Zero-shot LLM | RAG |
| --- | --- | --- | --- | --- |
| Тип задачи | классификация | классификация/извлечение | генерация | генерация с поиском |
| Нужны размеченные данные | Да | Да | Нет | Нет (нужны вопросы для оценки) |
| Ссылка на источник | Нет | Нет | Нет | Да |
| Обновление знаний | Переобучение | Переобучение | Промпт | Переиндексация |
| Галлюцинации | Нет | Нет | Высокий риск | Низкий при строгом промпте |
| Стоимость | Низкая | Средняя | Средняя | Средняя |
| Сложность | Низкая | Высокая | Низкая | Средняя |

Классический ML не подходит, потому что задача не сводится к классификации: ответ — свободный текст, а не метка. Fine-tuning encoder-модели потребовал бы большого набора пар «вопрос-ответ» и не дал бы ссылок на страницы; кроме того, знания устаревали бы при обновлении корпуса. Zero-shot LLM без поиска генерирует правдоподобные, но неподтверждённые ответы. RAG сочетает смысловое понимание вопроса, опору на материалы и проверяемые ссылки, поэтому выбран в качестве основного подхода.

## 3.4 Проектирование гибридного поиска

Поиск состоит из трёх этапов. Сначала по ключевым терминам определяется тема вопроса (Git, SQL, Linux, сети, ООП, алгоритмы, Computer Science). Если тема определена уверенно, обе ветви поиска ограничиваются этой темой; при низкой уверенности поиск идёт по всему корпусу, а совпадение темы даёт бонус к рангу. Это снижает шум от омонимов: например, «инкапсуляция» встречается и в сетях, и в ООП.

Плотная ветвь вычисляет эмбеддинг вопроса и ищет ближайшие чанки в ChromaDB по косинусной близости. Разреженная ветвь токенизирует вопрос и ищет по BM25 среди всех чанков корпуса. Перед объединением отбрасываются оглавления, предметные указатели и страницы с точечными выносками: они содержат термины вопроса, но не объясняют их и часто занимают верхние места в BM25.

Кандидаты объединяются взвешенной суммой:

score = 0,28·dense + 0,34·BM25 + 0,24·coverage + 0,14·RRF + бонусы,

где coverage — доля терминов вопроса, найденных в чанке; RRF — Reciprocal Rank Fusion; бонусы начисляются за совпадение темы, заголовка, точной фразы и конструкции определения («X — это», «X представляет собой»). MMR (Maximal Marginal Relevance) применяется к плотным кандидатам до объединения и снижает дублирование; λ = 0,55 смещён в сторону релевантности. Итоговый top-k = 4 передаётся в промпт.

Почему плотный индекс построен по подвыборке. Полный корпус содержит {{BM25_CHUNKS}} чанков; индексация всех чанков моделью USER2-base на CPU занимает несколько часов и требует большого объёма памяти. Поэтому для плотного индекса выбрана стратифицированная подвыборка: до 25 чанков на документ, равномерно по всей длине документа ({{DENSE_CHUNKS}} чанков). BM25 при этом покрывает все {{BM25_CHUNKS}} чанков. Такое решение сохраняет семантическое покрытие всех документов и одновременно обеспечивает точный поиск по полному тексту. Компромисс зафиксирован в разделе ограничений.

Схема гибридного поиска и объединения результатов показана на рисунке 3.2 (блоки «dense top-k + MMR», «BM25» и «взвешенное объединение»). В интерфейсе пользователь видит источники, страницы и оценки, поэтому может проверить, какая ветвь дала ответ.

## 3.5 Выводы по разделу

Выбран RAG с гибридным поиском, маршрутизацией по теме и стратифицированным плотным индексом.
