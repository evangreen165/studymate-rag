# 5 ОСОБЕННОСТИ РЕАЛИЗАЦИИ

## 5.1 Технологический стек

Стек выбран с учётом требований к RAG, воспроизводимости и возможности запуска на CPU. Все компоненты имеют открытые лицензии и хорошо документированы.

| Таблица: Технологический стек
| Компонент | Технология | Обоснование |
| --- | --- | --- |
| Язык | Python 3.12 | экосистема ML/NLP, поддержка библиотек |
| RAG-фреймворк | LlamaIndex | чанкинг, документы, интеграции с векторными БД |
| Векторная БД | ChromaDB | персистентность, метаданные, простой API |
| Эмбеддинги | USER2-base | русскоязычная модель, Apache-2.0 |
| LLM | Llama-3.1-70B через OpenRouter; Qwen2.5-7B локально | качество, контекст, офлайн-режим, доступность |
| Разреженный поиск | rank-bm25 | покрытие точных терминов и команд |
| API | FastAPI + Pydantic | валидация, OpenAPI, асинхронность |
| UI | Streamlit | быстрый чат-интерфейс, загрузка файлов, метрики |
| Контейнеризация | Docker, Docker Compose | воспроизводимость, один запуск |
| CI | GitHub Actions | линтер, тесты, сборка образа |
| Тесты | pytest, ruff | unit/integration, качество кода |

| Управление зависимостями | uv | быстрый lock-файл, Python 3.12 |

## 5.2 Реализация API

API построен на FastAPI. Все входные данные валидируются Pydantic: вопрос ограничен 2 000 символами, top-k — от 1 до 12, max_tokens — от 64 до 4 096. Ошибки возвращаются в едином формате с HTTP-кодом и понятным сообщением.

| Таблица: Эндпоинты API
| Метод | Путь | Вход | Выход |
| --- | --- | --- | --- |
| GET | `/health` | — | статус, версия, uptime |
| GET | `/ready` | — | готовность индекса, размеры |
| POST | `/chat` | вопрос, top-k, тема, провайдер | ответ, источники, токены, задержки |
| GET | `/documents` | — | документы, статусы, чанки |
| GET | `/topics` | — | темы и число документов |
| POST | `/corpus/upload` | PDF, тема | загруженные документы |
| DELETE | `/corpus/documents/{id}` | — | результат удаления |
| POST | `/index` | rebuild, doc_ids | статус задания |
| GET | `/index/status` | — | прогресс, ошибки |
| GET | `/stats` | — | индекс, корпус, провайдеры |
| GET | `/metrics` | — | Prometheus-метрики |

Пример ответа `/chat` содержит `request_id`, `answer`, массив `sources` (документ, страница, score, фрагмент), `usage` (prompt/completion/total tokens, tokens_per_second), `timings` (retrieval/generation/total) и `refusal`. Это позволяет UI показывать не только текст, но и стоимость ответа.

Логирование выполнено в формате JSON: время, уровень, `request_id`, метод, путь, статус, длительность, токены и модель. Логи пишутся в stdout и в `logs/app.log`, что удобно для последующего анализа. Метрики Prometheus включают число запросов, гистограмму задержек, токены и обратную связь.

Обработка ошибок: пустой или слишком длинный вопрос — 400/422; пустой индекс — 503; ошибка LLM — 502; неизвестный документ — 404. При недоступности основной модели выполняется одна попытка резервной модели; если и она недоступна, возвращается понятная ошибка.

## 5.3 Веб-интерфейс

Интерфейс реализован на Streamlit и состоит из четырёх вкладок.

**Чат.** Основной экран: история сообщений, поле ввода, примеры вопросов. Для каждого ответа показываются источники в раскрывающемся блоке, цитаты, страницы и оценки. Под ответом — строка метрик: общее время, время поиска, время генерации, токены входа и выхода, токены в секунду, провайдер и модель. Есть кнопки обратной связи «полезно / не полезно», которые сохраняются в журнал.

**Материалы и индекс.** Сводные метрики корпуса, распределение по темам, таблица документов с фильтрами по теме и статусу, загрузка новых PDF, выбор темы, запуск индексации, прогресс, отмена, полная переиндексация и удаление документа. Статусы: `indexed` (есть плотные векторы), `sparse_only` (только BM25), `scanned` (нет текста), `error`, `duplicate`.

**Метрики агента.** Сводка по всем чатам: число запросов, токены, средняя скорость, средняя задержка; графики токенов, токенов в секунду и задержки; журнал запросов с возможностью экспорта в CSV. Здесь же отображаются размеры индексов и параметры чанкинга.

**О системе.** Краткое описание архитектуры, ограничений, эндпоинтов и ссылка на репозиторий.

История чатов хранится в `data/chat_history/chats.json`: несколько диалогов, автоматический заголовок по первому вопросу, экспорт в Markdown, удаление. Это позволяет вернуться к обсуждению после перезапуска приложения. На рисунках 5.1–5.4 показаны основные экраны.

## 5.4 Контейнеризация

Сборка выполняется в два этапа. На этапе builder устанавливаются зависимости через `uv sync --frozen`, копируются исходники и скачивается модель эмбеддингов, чтобы контейнер не загружал 600 МБ при старте. На этапе runtime используется `python:3.12-slim`, создаётся непривилегированный пользователь, устанавливаются только необходимые системные библиотеки.

`docker-compose.yml` запускает два сервиса: `api` (порт 8000) и `ui` (порт 8501). API монтирует `data/`, `chroma_db_demo/` и `logs/`, UI — `data/` для истории чатов. Healthcheck проверяет `/health` и `/_stcore/health`; UI стартует после готовности API. Демонстрационный индекс собирается при первом запуске, если его нет. Одна команда `docker compose up --build` поднимает систему без ручной настройки окружения.

Для полного корпуса используется отдельный сценарий: PDF кладутся в `data/`, выполняются `scripts/build_manifest.py` и `scripts/build_index.py`, затем compose монтирует готовый индекс. Это позволяет не пересобирать индекс при каждом перезапуске контейнера.

## 5.5 CI и тестирование

GitHub Actions выполняет три шага: установка зависимостей через uv, линтер `ruff`, тесты `pytest` с покрытием и сборку Docker-образа. Тесты не требуют сети и платных API: используются mock-LLM и детерминированный эмбеддер. Отдельный smoke-тест проверяет чанкинг и индексацию на демонстрационном корпусе.

Покрыты: очистка текста, языковая статистика, чанкинг, промпты и цитаты, гибридный поиск, отказ при пустом индексе, API-валидация, успешный ответ, готовность, метрики. Интеграционные тесты с реальной моделью вынесены в отдельные маркеры и запускаются локально.

## 5.6 Производительность

Измерения проводились на CPU AMD Ryzen 5 5500U (6 ядер, 12 потоков), 17,8 ГБ RAM, без GPU. Для API измерялись p50 и p95 задержки, пропускная способность при concurrency 3–5 и потребление памяти контейнера.

| p50 ответа | {{P50}} с | — |

Основное время ответа приходится на LLM; поиск по индексу занимает десятки-сотни миллисекунд после загрузки модели эмбеддингов. Первый запрос после старта дольше, потому что загружается USER2-base; в Docker модель кэшируется в образе, что сокращает холодный старт. Локальная Qwen2.5-7B на CPU отвечает значительно медленнее (единицы токенов в секунду), поэтому используется как офлайн-вариант для сценариев, где важна приватность или нет доступа к облаку.

## 5.7 Безопасность и приватность

Секреты хранятся только в `.env`, который исключён из Git; в репозитории есть `.env.example`. CORS ограничен адресами UI. Входные данные валидируются по длине и типу; загружаются только PDF до 100 МБ, не более 50 файлов за раз. Имена файлов очищаются, путь не может выйти за пределы `data/uploads`.

Промпт содержит инструкцию игнорировать команды внутри фрагментов: это снижает риск prompt injection через PDF. В LLM отправляются только найденные фрагменты, а не весь корпус. Логи не содержат ключей и полных текстов документов; для анализа сохраняются идентификаторы запросов, токены и задержки.

## 5.8 Выводы по разделу

Реализованы REST API, веб-интерфейс, контейнеризация и CI. Интерфейс позволяет управлять корпусом и видеть метрики работы агента. Docker Compose поднимает систему одной командой; GitHub Actions проверяет код и сборку. Проведены измерения производительности и сопоставление с нефункциональными требованиями. Обеспечены базовая безопасность и приватность.
